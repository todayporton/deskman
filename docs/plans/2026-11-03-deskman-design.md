# deskman 設計

macOS のデスクトップ（Spaces）に任意の名前を付けて管理・移動する小さなユーティリティ。並べ替え、増減、ディスプレイの抜き差しがあっても、名前は同じデスクトップを指し続ける。後で Herdr モッドから CLI として呼び出す。

## 速度の要件

切り替えは瞬時が理想で、無理でも非常に高速であること。これは重要な要件で、方式の選択では互換性や実装の簡単さより優先する。各方式の切り替え時間を測って判断する。

InstantSpaceSwitcher（MIT）は、スワイプの進捗をほぼ 0（`0.000016`）にしてアニメーションする距離をなくし、Began、Changed、Ended の3段階を送っている。macOS 26 の範囲ではまずこの形を試す。Mission Control の操作など、遅い方式は採用しない。

## 方針

- Swift（SwiftPM）で作るバイナリ1つ。引数なしならメニューバー常駐、引数ありなら CLI として動く。
- `Deskman.app` として配布し、`~/.local/bin/deskman` からリンクする。
- yabai などの外部ツールには依存しない。不要な機能を設定で消すより、必要な部分だけ実装する。
- 非公式 API の使用を許容する。macOS の更新で壊れる可能性は受け入れ、影響範囲を `SpaceList` と `SpaceSwitcher` に閉じ込める。

## 構成

| 部品 | 役割 |
|---|---|
| `SpaceList` | `CGSCopyManagedDisplaySpaces` で一覧と現在地を取得する |
| `SpaceSwitcher` | 現在地との差分を計算し、Dock スワイプを合成して移動する |
| `NameStore` | UUID と名前の対応を読み書きする |
| `SpaceResolver` | 名前、番号、UUID から移動先を特定する |
| CLI | 下記のコマンド |
| メニューバー | 現在の名前の表示、移動、名前の変更 |

## 名前の保存

`~/.config/deskman/names.json` に `{ "<UUID>": "仕事" }` の形で保存する。

- 保存するのは UUID だけ。番号と数値 ID は保存しない。
- 名前はディスプレイをまたいで一意にし、重複は拒否する。
- フルスクリーンのデスクトップは一覧に出すが、名前は付けられない。
- 一覧にない名前は自動で消さない。手動で消すには `deskman rename --forget <名前>` を使う。

## CLI

```
deskman list [--json] [--all]  一覧（番号、名前、ディスプレイ、現在地）。--all は一覧にない名前も出す
deskman current [--json]       現在のデスクトップ
deskman go <名前|番号|UUID>    移動
deskman rename <対象> <名前>   名前を付ける（"" で解除）
deskman rename --forget <名前> 一覧にない名前を消す
```

番号は「今の並びの N 番目」を意味するので、並べ替えるとずれる。ずらしたくない呼び出しでは名前か UUID を使う。Herdr モッドは UUID で呼ぶ。

### 終了コード

| コード | 状況 |
|---|---|
| 0 | 成功（すでに目的のデスクトップにいる場合を含む） |
| 2 | 名前が見つからない |
| 3 | デスクトップが今の一覧にない（ディスプレイが外れている可能性を表示する） |
| 4 | アクセシビリティ権限がない（設定画面へ案内する） |
| 5 | 移動を確認できない |
| 6 | 名前の重複 |

エラーは標準エラーに出力する。

## 移動の流れ

1. 実行のたびに一覧を取り直し、目的の UUID を探す。
2. 同じディスプレイなら、差分の回数だけスワイプを送る。
3. 別のディスプレイなら、先にカーソルをそのディスプレイへ移してから送る。カーソルが動くのは既知の副作用。
4. 最大1秒、現在地を確認する。着いていなければ終了コード 5 を返す。

連続で呼ばれた場合は、最後の指定だけを実行する。

### スワイプの合成

yabai の `space_manager_focus_space_using_gesture` と同じ手法。`CGEventCreate` のイベントに次のフィールドを設定し、`kCGSessionEventTap` へ 1 ステップごとに Began（1）、Ended（4）の順で送る。

| フィールド | 意味 | 値 |
|---|---|---|
| 55 | イベント種別 | 30（DockControl） |
| 110 | HID 種別 | 23（DockSwipe） |
| 123 | スワイプ方向 | 1（水平） |
| 124 | 進捗 | ±1 |
| 129 | X 速度 | ±9999.0 |
| 132 | ジェスチャーの段階 | 1 または 4 |

macOS 26.2 ではまだ動作を確認していない。

## メニューバー

現在のデスクトップ名を表示し、ディスプレイごとの一覧から移動と名前の変更ができる。更新には `NSWorkspace.activeSpaceDidChangeNotification` を使い、ポーリングはしない。

## 実機で確認した事実

2026-11-03、macOS 26.2、ディスプレイ2台（メイン6個、外部7個）で外部ディスプレイを抜き差しした。確認は1回のみ。

| | 接続中 | 抜いた後 | 再接続後 |
|---|---|---|---|
| 外部で表示中だった `536AE57C…` | 7番 | 一覧から消える | 7番に戻る |
| 外部の残り6個 | 8〜13番 | メインに移り7〜12番 | 8〜13番に戻る |
| メインの6個 | 1〜6番 | 変化なし | 変化なし |
| `536AE57C…` の数値 ID | 16 | なし | 2465 に変化 |

- UUID は抜き差しをまたいで維持された。
- 数値 ID は変わることがあるので、保存してはいけない。
- 抜いている間に消える1個は移動できないので、終了コード 3 を返す。再接続すれば同じ名前で使える。
- 一覧取得の実行時間は約 20ms。

## VM での検証結果

2026-11-03、VM（macOS 26.6.2、ディスプレイ1台、4〜5デスクトップ）で確認した。ホストの macOS 26.2 とはバージョンが異なる。

- スワイプ合成は 3 段階、進捗 `0.000016`、速度 2000 で動く。正の符号が右。
- 間隔なしの連続送信でも取りこぼしなし。3つ先への移動は途中を経由せず、状態の変化まで約 40〜60ms。
- `deskman go` の全体（起動から確認まで）は 54〜94ms。すでに目的地にいる場合は 29ms。
- 連続キャプチャ（約 90ms 間隔、最初の 1 枚は約 150ms）で途中のスライドは写らなかった。通常のキー操作では同じ方法で大きな変化が写った。
- 並べ替え、追加、削除の後も名前は同じデスクトップを指した。削除されたものは終了コード 3。
- 先頭のデスクトップの UUID が空だった（ホストでは全 13 個に UUID あり）。番号がずれないよう一覧には残し、名前は付けられないようにした。
- フォーカスを移すための合成クリックは、他のウィンドウを押す危険があるので実装していない。

未検証: ホストでの速度、権限がない場合の動作（VM では全プロセスに権限があり再現できなかった）、Herdr から呼ぶ場合の権限、別ディスプレイへの移動、再起動後の UUID。

## 実機で分かったこと（2026-11-03、macOS 26.2）

- メニューバーからの移動はアニメーションなしで切り替わった。戻った後も Herdr のターミナルに入力できた。別ディスプレイへの移動ではカーソルが移動先へ動いた。
- Herdr のターミナルのプロセスは `zsh → claude → zsh → herdr-core` と続き、Herdr.app を経由しない。CLI から直接送ると権限エラー（終了コード 4）になった。
- `herdr-core` に権限を与えると、ターミナルで動く全プログラムが同じ権限を持つおそれがある。そのため CLI はローカルソケットで Deskman.app に移動を依頼し、権限は Deskman.app だけに持たせる構成に変更した。
- カーソルを残したい場合のために `go --restore-cursor` を追加した。スワイプはカーソルのあるディスプレイに効くので、移動後に元の位置へ戻す。
- ソケット版で確認済み: Deskman.app の権限だけで Herdr のターミナルから移動できる。`go --restore-cursor` で別ディスプレイへ移動でき、カーソルは元の位置に戻り、キーボード入力は Herdr に残る。「ログイン時に起動」のチェックが付く（実際の自動起動は未確認）。

未確認: Mission Control での並べ替えと増減（VM では確認済み）、外部ディスプレイを抜いている間に移ってきたデスクトップへの移動、再起動後の UUID と自動起動。

## 既存 OSS から得た未検証の注意点

2026-11-03 にソースを読んで確認した。いずれも他者の報告で、この Mac では試していない。

- spacelabel（MIT）: ディスプレイを抜いた後に別ディスプレイへ移ったデスクトップは、macOS 標準のショートカットでも移動できず、元に戻されることがある。スワイプでも起きるなら、抜いている間の移動は制限になる。
- spacelabel: フルスクリーンでも `type` が 0 で `TileLayoutManager` を持つことがある。UUID が空のデスクトップもある。
- spaces-manager（MIT）: スワイプを1ステップごとに送り、完了を確認して、取りこぼしたら再送している。
- spaces-manager: ターミナルから起動すると、アクセシビリティ権限はターミナル側に必要になる。
- macspacename（MIT）: `CGSSetSymbolicHotKeyEnabled` で「デスクトップ N へ切り替え」を一時的に有効にして送り、300ms 後に無効へ戻す。ユーザーの設定変更が不要で、別ディスプレイにも届くとしている。スワイプが使えない場合の代替候補。spacelabel は別ディスプレイへは届かないと報告しており、結果が食い違っている。
- macspacename: URL スキームで常駐アプリに移動を依頼するので、権限は常駐アプリだけで済む可能性がある。Herdr に権限を与えたくない場合の代替候補。ただし CLI へ結果を返す手段を別に用意する必要がある。

## Raycast の実装（2026-11-03、逆アセンブルで確認）

Raycast 2.10.1 の「Switch to Next/Previous Space」は、`RaycastMacOSUI/Display.swift` の `setCurrentSpaceWithoutAnimation(at:)` で実装されている。公式マニュアルに仕組みの記載はなく、本体のバイナリを逆アセンブルして読んだ。deskman と同じく Dock スワイプの合成で、`CGSManagedDisplaySetCurrentSpace` のような直接の切り替え API は使っていない。

- 移動の数だけ、1ステップごとに Began（1）、Changed（2）、Ended（4）を送る。各段階で DockControl イベントを送った直後に、フィールド 55 を 29（Gesture）にしただけの付随イベントを送る。
- 速度は macOS 27 以上なら 9999.0、それ未満なら移動数 × 999999.0。
- `if #available(macOS 27, *)` で形式を分けている。

### macOS 26 以前の形式

| フィールド | 値 |
|---|---|
| 55 / 110 | 30 / 23 |
| 132 | 段階 |
| 135 | 正の向きなら 1、逆なら −2147483647 |
| 123 | 1 |
| 119 / 130 | 0.0 |
| 129 | ±速度 |
| 139 | 1.4e-45（float の最小値） |

フィールド 124（進捗）は設定しない。

### macOS 27 以降の形式

1. 符号を決める。`com.apple.swipescrolldirection`（ナチュラルスクロール）が有効か未設定なら −1、無効なら +1。向きが逆ならさらに反転する。進捗 p = 符号 × 0.000016。
2. フィールドを設定する: 55=30、110=23、132 と 134 に段階、135 に `Int64(Int32(bitPattern: Float(p).bitPattern))`、123=1、115=0、124=p、125=0.1、126=0、130=0、138=3.0、169=`Double(mach_absolute_time())`。Ended だけ 129=±9999。
3. `CGEventCreateData` の出力の末尾に、長さ（UInt16 big-endian）、タグ 4205（UInt16 big-endian）、HID の DockSwipe イベントの順に足し、`CGEventCreateFromData` で作り直して送る。ヘッダの書き換えはしない。
4. HID イベントは 68 バイトの little-endian。IOKit の IOHIDEventData と同じ並びに見える。

| オフセット | 型 | 値 |
|---|---|---|
| 0 | u64 | `mach_absolute_time()` |
| 8 | u64 | 0（senderID） |
| 16 | u32 | 0（options） |
| 20 | u32 | 0（属性の長さ） |
| 24 | u32 | 1（イベントの数） |
| 28 | u32 | 40（size） |
| 32 | u32 | 23（type: DockSwipe） |
| 36 | u32 | 段階 << 24 |
| 40 | u8×4 | 0（depth, reserved） |
| 44 | i32 | 0x1999（16.16 の 0.1） |
| 48 | i32×3 | 0 |
| 60 | u16 | 1 |
| 62 | u16 | 3 |
| 64 | i32 | 16.16 の p。切り捨てで 0 になる値は ±1 にするので、実際は ±1 |

Ended で速度の子イベント（size 28、type 9、depth 1）を足す分岐もあるが、Raycast はそのフラグを 0 で呼んでおり使われていない。

deskman は macOS 27 以上でこの形式を送る（`SpaceSwitcher.MacOS27`）。macOS 27 の環境がないため、切り替わるかは未確認。

### VM での比較（macOS 26.6.2、デスクトップ4個）

`spike/swipe.swift` に `raycast`（26 以前の形式）と `hid`（27 以降の形式）を足して比べた。各1回。

| 形式 | 右1 | 左1 | 右3 | 左3 |
|---|---|---|---|---|
| deskman の現在の形式 | 57ms | 70ms | 44ms | 184ms |
| raycast | 53ms | 73ms | 38ms | 186ms |

- raycast の形式は速さが変わらないので、macOS 26 では deskman の形式のままにする。
- 先頭のデスクトップ（UUID が空）へ戻る移動は、どちらの形式でも約 185ms かかった。
- 端を越える回数を送ると遅くなる。3番目から右へ3つ送ったときは、4番目に着くまで 1399ms かかった。deskman は差分の回数だけ送るので、通常は起きない。
- hid の形式も macOS 26 で切り替わり、途中を経由しなかった（44〜76ms、1回だけ 283ms）。ただし向きが逆になった。VM はナチュラルスクロールが未設定なので符号が −1 になり、フィールド 124 が負になるため。macOS 27 では HID イベントの向きを指の動きとして扱うので、Raycast が符号を反転していると推測しているが、確認はしていない。

## Mission Control に名前を出す検証（2026-11-03、VM macOS 26.6.2、spike/mission-control.swift）

Mission Control のデスクトップ名は Dock が描いていて、書き換える手段は Dock へのコード注入（SIP の無効化が必要）しかない。そこで、名前の上に自分のウィンドウを重ねる方式を試した。

- Mission Control の表示中だけ、Dock のアクセシビリティ要素に `id=mc`（title=Mission Control）のグループが現れる。中は `mc.display`（ディスプレイごと）→ `mc.spaces`（Spaces Bar）→ `mc.spaces.list` で、その子がデスクトップごとのボタン（title=Desktop N、desc=exit to Desktop N）。
- バーが開いているとき（カーソルが上端にあるとき）は、ボタンの枠がサムネイル（144x90）で、名前はその下に描かれる。ボタンの位置は表示と一致した。
- バーが折りたたまれているときは、ボタンが名前そのもの（65x24 前後）になる。x と幅は表示と一致したが、y は表示より 40pt 上（-32）を返した。バー（`mc.spaces.list`、高さ 40）の縦の中央に置くと一致した。
- カーソルを乗せてバーが開くと、ボタンの位置は 100ms 以内に新しい値に変わった。開くときの途中の位置は返さず、最初から最終位置を返す。
- ウィンドウレベルを overlay、collectionBehavior を `.canJoinAllSpaces, .stationary` にした NSPanel は、Mission Control の表示中も縮小されずに最前面に出て、元の名前を覆えた。閉じるとすぐ消せた。
- Dock の AXObserver では、作成・破棄・フォーカス・選択の変更を登録できたが、Mission Control の開閉ではどれも届かなかった。レイアウトや値の変更などは登録できなかった（-25207）。検知は問い合わせを繰り返すしかない。
- 問い合わせの負荷（閉じている間）: 30ms 間隔で spike 約 0.8%・Dock 約 0.8%、100ms 間隔で spike 約 0.1〜0.3%・Dock 約 0.3%（CPU）。
- 未確認: ディスプレイ2台（`mc.display` が2つになるはず）、フルスクリーンのデスクトップ、開閉アニメーション中の見え方、並べ替えのドラッグ中、実機での体感。

本体への組み込み（`MissionControlOverlay.swift`、対応付けは `MissionControlLabels.swift`）:

- メニューの「Show Names in Mission Control」（既定はオン）で、0.1 秒ごとに問い合わせる。名前を付けたデスクトップだけを覆い、名前のないものは元の表示のままにする。
- 各 `mc.display` の枠と一致するディスプレイの UUID で、ボタンの並びをデスクトップの並びに対応付ける。ボタンとデスクトップの数が合わないディスプレイには何も出さない。
- 並びと名前は Mission Control を開いたときに読み、開いている間は位置だけを追う。
- Dock の要素は使い回し、問い合わせに失敗したら探し直す（Dock の再起動後も表示されることを VM で確認）。毎回 Dock のプロセスを探していたときは閉じている間の CPU が約 0.6% だったが、使い回して約 0.35%（Dock 約 0.1%）になった。
- 重ねた名前はクリックを通すので、その上をクリックしても Mission Control でそのデスクトップへ移れる（VM で確認）。
- 折りたたまれたバーでは、表示中のデスクトップのハイライトがボタンより左右に 10pt ずつ広い。名前をボタンの幅で覆うとハイライトがはみ出すので、どの名前もこの幅で覆う（隣との隙間は 12pt 残る）。表示中のデスクトップの名前はアクセントカラーの地にする。
- 並べ替えのドラッグの後、デスクトップの並び（CGSCopyManagedDisplaySpaces）とボタンの並びはどちらも閉じる前に変わる。並びは毎回読み直し、名前だけを開いたときに読む（VM で追従を確認）。
- 2026-11-04、表示を変えた（ユーザーの希望）: 名前はデスクトップのボタンの真上で、画面の上端に置く。上は角、下は角丸（半径 10）のノッチの形で、上から降りてきて、閉じると上へ引っ込む。パネルは最終位置に置き、中の図形だけを動かす（パネルを画面の外へ動かすと、上にある別のディスプレイに出てしまうため）。
  - ノッチの大きさは開閉で変えず、位置だけを動かす。幅は、折りたたまれたバーでボタンの中心の間隔の最小から 4pt 引いたもの（隣と重ならない最大、VM で 93pt）。折りたたまれたバーを見たときにディスプレイごとに覚え、まだ見ていなければ 90pt。
  - 高さは 34pt。折りたたまれたバーの元の名前と表示中のハイライトは上端から約 34pt まであり、26pt では下からはみ出した。バーが開いているときは、上端から 28pt 下のサムネイルに少し重なる（ユーザーの判断）。文字は枠の縦の中央。縁は白 25% の 1pt で、左右と下だけに引く（上端には引かない）。
  - 降りる 0.14 秒、引っ込む 0.15 秒。バーの開閉での横の動きは、プレビューの展開に追いつくよう一定の速さで 0.1 秒にする。パネル自体を動かすアニメーションでは速さの指定が効かずイージングが付いたので、パネルはディスプレイの上端の帯に固定し、中のノッチだけを動かす。また、開いている間は問い合わせを 0.03 秒間隔にする（閉じている間は 0.1 秒のまま）。
  - 名前を付けていないデスクトップも、メニューと同じく「Desktop 番号」を出す。フルスクリーンのデスクトップには出さない。
  - VM で、どちらの状態でも上端に出て元の名前が隠れ、表示中のデスクトップがアクセントカラーになることを確認した。スクリーンショットが間に合わず、動きそのものは VM では確かめられていない。

## ウィンドウを別のデスクトップへ運ぶ検証（2026-11-04、VM macOS 26.6.2、spike/move-window.swift）

非公式 API でウィンドウを別のスペースへ移す方法（`CGSMoveWindowsToManagedSpace` など）は、macOS 14.5 前後から他のアプリのウィンドウには効かなくなったとされ、試していない。タイトルバーを掴んだままデスクトップを切り替え、ウィンドウを運ぶ方法（Amethyst などと同じ）を試した。

- 掴む位置は、拡大ボタン（AXZoomButton）の右端から 12pt 右、ボタンの縦の中央。Finder のウィンドウで掴めた。
- マウスイベントは `CGEventSource(stateID: .hidSystemState)` で作り、クリック回数（mouseEventClickState）を 1 にして `.cghidEventTap` に送る。イベントソースなしで `.cgSessionEventTap` に送ったときは、ほとんど掴めなかった（成功は 3 回だけで、条件は分からなかった）。変えた後は 6 回続けて成功した。
- 掴んでいる間は、Dock スワイプの合成による切り替えが効かない（1 秒待っても切り替わらない。掴めているときも同じ）。
- 送り方を変えても効かなかった（2026-11-04 追試、各 1.5 秒待った）: HID の段に送る、Gesture イベントを添える（macOS 27 向けと同じ）、Changed を 16ms 間隔で 10 回送るゆっくりしたスワイプ、掴んだ後に少し動かすドラッグを省く、およびこれらの組み合わせ。spike の `swipe=hid+gesture` などの引数で再現できる。
- キーボードショートカット Control+→ / Control+←（「右／左の操作スペースに移動」、既定で有効）なら切り替わり、ウィンドウが運ばれる。アニメーションが付き、1 ステップ約 330ms（掴む時間を含めて約 400ms）。
- 続けて 2 回送ると掴んだ状態が外れ、ウィンドウは運ばれなかった。1 ステップごとに着いたのを確かめてから次を送ると、3 ステップ（約 1 秒）でも運べた。
- 掴み損ねたときは、1 ステップに約 620ms かかった（ウィンドウを運ぶときの方がアニメーションが短いと見ている）。
- 着いてから 50ms 待って離すと、ウィンドウのスペースが行き先に変わった。
- 元のデスクトップへ戻る（`--stay`）スワイプは、離した直後だと効かないことがあった（1 回失敗）。離してから 50ms 空けると 4 回とも戻れた。戻るスワイプ自体は約 30ms。
- 未確認: ディスプレイをまたぐ移動、フルスクリーンのデスクトップ、タイトルバーのないウィンドウ、ショートカットを無効にしている環境、「デスクトップ N へ切り替え」（Control+数字、既定で無効）を使って 1 回で移ること。

本体への組み込み（`deskman move`、`WindowMover.swift`）:

- ソケットの要求に `moveWindow` と `stay` を足した。古い CLI の要求もそのまま読める。何ステップも運ぶと 3 秒を超えるので、`move` の応答は 30 秒まで待つ。
- 同じディスプレイの中だけを運ぶ。途中のフルスクリーンのデスクトップも 1 ステップとして通る。行き先がフルスクリーン、元のデスクトップがフルスクリーン、別のディスプレイなら終了コード 8 で断る。
- 運んだ後、ウィンドウのスペース（`CGSCopySpacesForWindows`、`SystemSpaces.swift` に置いた）が行き先になったかを確かめ、なっていなければ終了コード 5。
- Control+数字のショートカットは、ユーザーの判断で当面使わない。
- 実機（この Mac）では「左／右の操作スペースに移動」（AppleSymbolicHotKeys の 79／81）を Control+Option+矢印に変えたうえでオフにしていて、80／82（Control+Option+Shift+矢印）がオンだった。Control+矢印を決め打ちで送っていたため、`move` は切り替わらずに失敗した。
- 79／81 の設定（com.apple.symbolichotkeys）を読み、キーと修飾キーをそのまま送るようにした（`SpaceShortcuts.swift`）。項目がないか、`enabled` だけでキーの指定がない項目は既定の Control+矢印として扱う（VM は後者だった）。オフなら終了コード 8。
- 80／82 は、VM で有効にして Control+Option+Shift+矢印を割り当てても切り替わらなかったので使わない。79／81 を画面から Control+Option+矢印に変えると、その組み合わせでウィンドウを運べた（VM で確認）。
- 常駐アプリは一度読んだ他のアプリの設定を覚えているので、読む前に `CFPreferencesAppSynchronize` で読み直す。
- 設定ファイルを直接書き換えても、Dock が使うショートカットは変わらないことがあった（画面で変えると反映された）。設定ファイルと Dock がずれていると、切り替わらずに終了コード 5 になる。途中で失敗したときは元のデスクトップへ戻る。
- VM で設定を書くときの注意: `defaults write` の辞書の書き方では数値が文字列で入る（読み取りは文字列も受け付けるようにした）。VM のシェルは zsh なので、`$k:enabled` のような書き方は修飾子として解釈される（`${k}` と書く）。
- 0.3.0 の常駐アプリは `moveWindow` を読み飛ばし、`move next --stay` をただの `next` として実行した（実機で発生）。CLI は運ぶ前に `ping` の要求を送り、成功しなければ終了コード 7 で止める。古い常駐アプリは `ping` を空の名前の移動として扱い、「見つからない」を返すだけで何も動かさない。
- 実機ではショートカットがオフのままでも、Raycast の「Move to Next/Previous Desktop」は動いていた。Raycast 2.10.1 のバイナリは `CGSGetSymbolicHotKeyValue`、`CGSIsSymbolicHotKeyEnabled`、`CGSSetSymbolicHotKeyEnabled` を参照し、「Unable to restore symbolic hotkey disabled state」という文字列を持つ。キーを WindowServer から読み、オフなら一時的にオンにして送り、元に戻していると判断した（逆アセンブルでの流れの確認はしていない）。
- 同じ方法に変えた。VM で 79／81 を `CGSSetSymbolicHotKeyEnabled` でオフにすると、キーを送るだけでは切り替わらず（3 秒待って失敗）、一時的にオンにすると 1〜3 ステップとも運べた。`move next`、`move 4 --stay`、`move 1` も通り、終わった後は 79／81 がオフに戻っていた。オンとオフはこのログインの間だけの状態で、設定ファイルは変わらない。
- WindowServer から読むので、設定ファイルの解析（上の `SpaceShortcuts` の読み取りと文字列の扱い）はやめた。VM の「`enabled` だけでキーの指定がない」項目も、WindowServer からは既定の Control+矢印（キー 123／124、修飾 0x840000）として読めた。キーがない（キーコード 0xFFFF）ときだけ終了コード 8。
- 実機で、運べるウィンドウと運べないウィンドウがあった（終了コード 5、デスクトップだけ切り替わる）。拡大ボタンの右はツールバーやタブが置かれるアプリがあるため。Raycast は閉じるボタンと `AXMinimizeButton` を読み、赤と黄色のボタンの間の上寄りを掴んでいる（ユーザーの観察）ので、同じく閉じるボタンと最小化ボタンの間の中央、閉じるボタンの上から 1/4 の高さを掴むように変えた。最小化ボタンがなければ閉じるボタンの右 3pt。閉じるボタンがなければ「タイトルバーがない」の終了コード 8。
- 実機（ディスプレイ 2 台、2 台目のデスクトップ 4 と 5、Chrome）で、進む向きの片方だけを一時的にオンにしてすぐ送ると、右は運べたが左は切り替わらなかった。キーはどのイベントタップにも止められず最後まで届いていた（左右とも flags 0xac0000）。手で押すと左も効き、設定でオンにしておけば運べた。左右の両方をオンにし、50ms 待ってから送るように変えると、オフのままで左右とも運べた（1 ステップ約 0.37 秒）。片方だけでは効かなかった理由は分かっていない。
- 掴んだ直後に 1pt 右へ動かして戻すドラッグを送っていたが、戻す方が効かず、掴んでいる間ウィンドウが 1pt 右へずれていた（実機で気付いた。離すと戻る）。VM でこのドラッグを省いても 4 回とも運べ、位置も変わらなかったので省いた。
- 実機での状況を追えるよう、`WindowMover` は運ぶたびにシステムのログへ記録する（`log show --predicate 'subsystem == "online.todayporton.deskman"'`）。
- 未対応: 運ぶ途中でプロセスが落ちると、オフだったショートカットがオンのまま残る（次のログインで設定ファイルの値に戻る）。Raycast は「Switching space with modifiers still held」と警告しており、修飾キーを押したまま呼ぶと別のショートカットとして扱われうるが、deskman では確かめていない。
- VM で、名前・`next`・`prev --stay`・番号への移動を確認した（1 ステップ約 400ms、`--stay` 約 490ms）。ウィンドウのないデスクトップでは、Finder のデスクトップ用のウィンドウに拡大ボタンがないため「タイトルバーがない」の終了コード 8 になった。


- **単体テスト:** 一覧部分を差し替えられるようにし、上記の実測3パターンをテストデータにする。名前の解決、差分の計算、重複の拒否、一覧にない場合の終了コードを確認する。
- **VM（`macvm`）:** 切り替えの動作、権限がないときの案内、メニューバーの表示を確認する。最初にスワイプの合成が動くかを試し、動かなければ方式を見直す。
- **ユーザーによる実機確認:** 別ディスプレイへの移動、カーソルの移動、Mission Control での並べ替え、デスクトップの増減、再起動後の UUID。切り替えを伴う操作は、開発中に自動でホストの Mac に対して実行しない。
